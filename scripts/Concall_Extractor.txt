## CONTEXT

Gemini-powered concall extraction pipeline. Each PDF transcript is processed
through concall_prompt.txt → structured intelligence stored in Google Drive.
Prompt extracts: Table_A (financial grid + guidance), GF1 (raw forward
statements), GF2 (historical guidance vs actuals), GF3 (operational
visibility), GF4 (guidance quality flags), A1/A2/A3 (summaries),
B/C/E1 (growth drivers, management commentary, forward visibility).

### Capacity Analysis Ask   ✅ DONE
Ask: Check how many Gemini keys are active. If 100 concalls + 100
presentations/results per day, do we have bandwidth? What if we hit a monthly
limit like GitHub Actions? Provide a conservative estimate for the full month.
"Your assumption were wrong yesterday — 8 companies took 40 mins, not 8-10 min."

Delivered findings:
  - 6 Gemini API keys confirmed active in environment
  - Corrected timing model: ~2 min/concall all-in (Gemini call + Drive I/O +
    amortised 429 wait). Previous estimate of 8-10 min/run was wrong.
  - Daily quota: 6 keys × 250 RPD = 1,500 req/day available.
    Peak load (100 concalls + 30 other docs) = 130 req/day = 8.7% utilisation.
    No daily quota risk.
  - Monthly quota: Gemini 2.5 Flash free tier has NO monthly request cap.
    Only the daily 250 RPD limit applies. No GitHub-style monthly bucket.
  - Root cause of 429 cascades: RPM (10 req/min per key), not daily exhaustion.
    Fix: INTER_CALL_SLEEP = 6 sec between calls. Eliminates ~90% of cascades.
  - Peak season throughput: 100 concalls/day across 5 runs ≈ 200 min/day total.
    Each run ~43 min. Well within 180 min timeout. No risk.

  Layer 1 — phase2.yml schedule updated from 29 to 47 runs/week:
    Weekdays: 10/12/14/16/18/20/22 IST (every 2h) + 03:00 IST overnight = 8/day
    Saturday: 10/12/14/16/18 IST = 5/day
    Sunday: 10/14 IST = 2/day
    More opportunities = shorter gaps even if individual slots are delayed.
  Layer 2 — daily.yml backup trigger:
    At end of every Phase 1 run (IST ~17:00), a new step dispatches phase2.yml
